## 4A-2 Order 与事件 Java 封装

实际生成的 Escrow.Order extends DynamicStruct。buyer/seller/token/description 为 String，
amount/deadline/status 为 BigInteger。uint8 status 也被解码为 BigInteger；Service 将它映射成状态文字。
ORDERCREATED_EVENT 记录事件名、参数类型与 indexed 标记：id、buyer、seller 在 topics 中，
token、amount、deadline 在 data 中。EventEncoder.encode 得到事件签名 topic0，用来过滤日志；
getOrderCreatedEventFromLog 再按该 ABI 把 topics/data 还原成字段。
BINARY 为部署字节码，FUNC_* 为函数名常量；这些都由生成器产生，不手工改生成类。
证据：成员 1 的 [Order 类截图](../evidence/member1/screenshots/4A-2b_文件列表与Order结构.jpg)
和 [事件解码截图](../evidence/member1/screenshots/4A-2c_OrderCreated事件解码.jpg)。
结合本组 [Paid 状态核验图](../evidence/potos/screenshots/4A-5-buyer-paid-verification.jpg)，
订单 0 的 amount 为 30000000000000000000，statusCode 为 1，Service 对外返回 Paid。
18 位精度换算后金额是 30 个。Java 中用 BigInteger 保存最小单位，不能改成浮点金额。
OrderCreated 只记录创建信息，不包含当前状态；状态仍由 getOrder 查询。

## 4A-3 订单列表与 RPC 次数

循环 getOrder 需要 N 次读取；若先读 orderCount，总共 N+1 次。当前 Service 从事件取得创建记录，
包括 transactionHash、blockNumber，无需逐笔查询状态，也不会假定订单来自某个应用。
但 POTOS 教程要求每次只能扫描 10 个区块，因此事件查询不是永远只需 1 次 RPC。
部署区块 D、查询时块高 H 时，当前实现为 1 次 eth_blockNumber 加 ceil((H-D+1)/10) 次 eth_getLogs。
首次 load 的 chainId/getCode 校验另算；列表每次调用都重新扫描，尚未实现增量缓存。
因此 1 万笔订单的比较取决于跨了多少区块，不能笼统说事件法总是更少请求。
本地单元测试覆盖 100..122 三个闭区间：100..109、110..119、120..122。
这些是本地边界测试输入。本组正式数据可用以下截图做计算示例：
[部署截图](../evidence/potos/screenshots/4A-5-escrow-deploy-address.jpg)中的 D=2821876，
[付款核验图](../evidence/potos/screenshots/4A-5-buyer-paid-verification.jpg)中的快照块高 H=2822836。
若 listOrders 的 latest 正好取该快照块，则闭区间共有 961 块，需 97 次 eth_getLogs，
加 1 次 eth_blockNumber，共 98 次；已有两笔订单，用 orderCount+两个 getOrder 是 3 次。
这里的 98 是按实现与截图块高计算出的例子，**不是声称实际 GET 预检逐次记录了 98 个请求**。

若有 1 万笔订单，循环方式需 10001 次（已有 orderCount 时为 10000 次）；
本实现事件方式仍取决于部署以来的区块跨度，公式不随订单数直接变成 1。
事件法在这里的价值是按教程从 OrderCreated 重建创建列表，取得交易哈希和区块号，
并可作为以后做增量索引的基础。当前实现尚无增量缓存，不宣称它在所有情况下都更快。

## 4A-4 失败仲裁 回执与 Gas

先由卖家将订单 1 变成 Disputed，再完成三条 GET；订单 0 仍是 Paid。
BE 对订单 0 调用 resolve(0,true) 会违反 inStatus(Disputed)，对应合约原因 Escrow: wrong status。
Web3j 的 TransactionException 可能携带失败回执；异步调用还可能在外层包一层 CompletionException。
Controller 会向下取 cause 并查找回执，链上回滚映射 HTTP 409；有回执时保留
transactionHash、blockNumber、status、gasUsed。网络故障归为 502，不与合约状态错误混淆。

若实际得到已入块回执且 status=0x0，可据此证明失败交易上链，状态修改回滚；
gasUsed 是消耗的执行 Gas，实际 POT 费用须结合链上的有效 Gas 单价与账户余额核对。
签名发送者为 BE，因此链上交易费由 BE 承担。若仅在广播前失败且没有交易哈希/回执，
不能据此声称已经上链扣费。当前使用固定 Gas 上限，仍应以实际回执为准。

恶意调用一万次可能持续触发签名、占用服务器与 RPC，并在交易入块时消耗 BE 的测试币，
也可能因余额不足、nonce、RPC 限制等失败；不能直接假定一万次全部入块。
若同类失败每笔实际耗费 F，则一万笔都入块的费用估计为 10000×F，不能以 gasLimit 代替 gasUsed。

实际交易：0x6b6157111ef72bcacf69ab031d15ccaebd11cde978fa73637eebde039117f4c3，区块2823579、status=0x0、gasUsed=25884、effectiveGasPrice=0，执行手续费为0 POT。成员3终端记录图显示HTTP409；message中的Revert reason为空，wrong status是根据源码和前置状态判断，不能冒充异常原文。回执无日志，当前订单0仍为Paid。操作人袁嘉骏，成员1提供后端，BE签名。

原始回执见evidence/potos/records/arbitration-verified-receipts.json。HTTP状态来自截图，未收到原始HTTP文件。两笔均已入块，但零有效Gas单价下，本次不能声称BE实际被扣除正数POT。

## 4A-6 无认证接口的风险与合约权限边界

至少需要两层控制。第一层在 API：身份认证、仲裁角色授权、针对具体订单的审批，
拒绝普通用户直接触发服务器签名，并增加限流、审计和重复请求控制。
第二层在签名/密钥管理：专用签名服务或受控密钥存储，限制可调用合约、函数、金额和网络，
重要仲裁需要独立复核；合约层还可设计多签或更明确的争议处理规则。
这些是改进建议，当前课程项目尚未实现，不能写成已有功能。

本组证据是部署图中的 arbiter=0x4c688b060912faf95324a43C0190C59E7cE8aB3c，
以及 [付款核验图](../evidence/potos/screenshots/4A-5-buyer-paid-verification.jpg)中两笔各 30、总计 60 个代币托管。
攻击者若能调用未认证的 resolve 接口，可借服务器的 BE 身份尝试行使仲裁权；
若 BE 私钥直接泄露，则能绕过 API，自行签名。

但本合约的 arbiter 没有“提走全部余额”函数：resolve 只接受 Disputed 订单，
只能把该订单 amount 转给预先写入的 buyer 或 seller，不能指定新的任意收款地址。
在本组两笔仍为 Paid 的快照状态下，仅有 BE 私钥无法直接 resolve 这两笔，
BE 也不是买家或卖家，不能以 BE 身份把它们变为 Disputed。
当某订单进入 Disputed，攻击者可滥用 sellerWins 改变约定双方谁收款，并能盗用 BE 自有资产/消耗其 Gas。
因此“不能把 Escrow 里的全部代币任意转给自己”不等于没有严重风险。
