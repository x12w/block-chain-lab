## 部署与加载

1. 确认第二仲裁地址与BE不同且非零，准备足够测试POT支付可能产生的Gas。部署响应和回执为正式地址的唯一来源。
2. 在已运行的后端调用一次 `/deploy-enhanced?secondArbiter=实际地址`。记录新合约地址、部署块、部署交易哈希。请求超时先查回执和 `/address`，避免重复部署。
3. 查询 `/arbitrators`，核对第一、第二仲裁地址及 `requiredVotes=2`。
4. Remix中保存仓库的 `Escrow.sol` 和 `EscrowEnhanced.sol` 到同一目录，编译后选择EscrowEnhanced，用At Address加载新地址。不要把旧Escrow地址当作增强合约。
5. 后端重启时，用 `/load-enhanced?address=新地址&fromBlock=实际部署块` 恢复绑定。

可复制命令（把变量换成部署记录中的实际值）：

```bash
BASE=http://127.0.0.1:8080/api/escrow
# SECOND_ARBITER填写袁嘉骏提供的公开地址后，仅执行一次：
curl -sS -X POST "$BASE/deploy-enhanced?secondArbiter=$SECOND_ARBITER"
curl -sS "$BASE/arbitrators"
```

## 发货与退款证据

买家创建三笔各1个WQLToken的订单：发货后确认、未发货超期退款、发货后争议退款。金额整数为1000000000000000000，卖家填写张俊仁原地址；期限统一用当前链上时间加15分钟，事先保证组员在线。买家先向新合约approve总计3个，等待成功后分别deposit。

1. 卖家在截止前对第0、2笔调用 `markShipped`。保存成功回执、`OrderShipped`事件、状态Shipped。
2. 使用非卖家账户尝试发货，应被权限检查拒绝；保存实际错误，不把钱包模拟拒绝说成已上链失败交易。
3. 截止时间过后，第0笔买家尝试refund应失败，第1笔买家refund应成功，保存两者结果及状态。第1笔应Refunded。
4. 第0笔由买家confirm，保存成功回执、Completed和卖家收到1个代币的记录。
5. 第2笔由卖家dispute，核对Disputed后进入下一节。

每笔发送前核对当前账户、新合约、订单ID和状态。钱包如报告模拟失败，保留错误即可，不为制造失败回执强制发送交易。网络或页面超时先查询实际回执与状态，再决定下一步。

## 两人投票证据

对第2笔Disputed订单，约定最终退款给买家，即 `sellerWins=false`。

1. 第一仲裁BE通过后端 `POST /orders/2/resolve?sellerWins=false`投票。保存HTTP响应、回执和 `/orders/2/votes`。此时只有一票，订单应仍Disputed、托管代币不变。
2. 袁嘉骏用本人钱包在Remix的新EscrowEnhanced上调用 `resolve(2,true)`，用于展示意见不一致。保存成功回执和投票详情；订单应仍Disputed，资金仍未结算。
3. 袁嘉骏将意见改为 `resolve(2,false)`。两票一致后订单变为Refunded，应产生 `ArbitrationVoted`、代币Transfer和 `OrderResolved`。保存买家收款和合约余额。
4. 查询 `/orders/2/events`，核对创建、付款、发货、争议、各次投票、最终裁决的顺序与交易哈希。第一次投票或意见冲突时的HTTP200只代表投票交易成功，不能写成仲裁已完成。

第2步的冲突演示是为验证“两人一致”的条件，两个参与者需知晓演示顺序；任何一票不一致都不会自动付款。每次操作后先等交易成功并核对状态。
