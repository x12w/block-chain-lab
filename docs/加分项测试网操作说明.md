## 先在Remix准备

1. 使用装有买家MetaMask的钱包浏览器打开Remix，连接POTOS Testnet，选中`0x5a435c43Ca006bE1688d0D7B95194327528EAB26`。
2. 导入仓库`docs/BonusAcceptanceInterfaces.sol`并使用0.8.x编译器编译。它是与已部署合约匹配的接口，无外部依赖。
3. Deploy & Run中选择`IRouteABonus`，在At Address填写增强合约地址并加载；不点Deploy。
4. 再选择`IRouteABonusToken`，At Address加载WQLToken地址。只读检查`version=2`、`arbiter`、`secondArbiter`、`orderCount`、买家`balanceOf`。部署核验时订单数为0，后续应以当时读数为准。
5. 后端重启才需要执行下方load命令。当前已经加载，不必重复切换。

后端恢复命令：

```bash
BASE=http://127.0.0.1:8080/api/escrow
curl -sS -X POST "$BASE/load-enhanced?address=0x917Dc833eadBa6544F1fd80498715da39Ac739f4&fromBlock=2829547"
curl -sS "$BASE/arbitrators"
```

## 发货与退款证据

先确认卖家在线，再由买家创建三笔各1个WQLToken的订单：发货后确认、未发货超期退款、发货后争议退款。金额整数为`1000000000000000000`，卖家、代币填写上表地址；期限使用操作开始时的链上时间加15分钟，不复用旧时间戳。描述依次用`bonus shipped confirm`、`bonus unshipped refund`、`bonus shipped arbitration`。买家的3个代币授权已完成，核对allowance后分别deposit。所有调用的原生币Value为0。

下面以新合约最初三笔订单ID为0、1、2说明。每笔创建后核对实际OrderCreated事件ID；若订单数已经变化，按真实ID操作，不能重复创建或猜测编号。

1. 卖家在截止前对第0、2笔调用 `markShipped`。保存成功回执、`OrderShipped`事件、状态Shipped。
2. 使用非卖家账户尝试发货，应被权限检查拒绝；保存实际错误，不把钱包模拟拒绝说成已上链失败交易。
3. 截止时间过后，第0笔买家尝试refund应失败，第1笔买家refund应成功，保存两者结果及状态。第1笔应Refunded。
4. 第0笔由买家confirm，保存成功回执、Completed和卖家收到1个代币的记录。
5. 第2笔由卖家dispute，核对Disputed后进入下一节。

每笔发送前核对当前账户、新合约、订单ID和状态。钱包如报告模拟失败，保留错误即可，不为制造失败回执强制发送交易。网络或页面超时先查询实际回执与状态，再决定下一步。

## 两人投票证据

对第2笔Disputed订单，约定最终退款给买家，即 `sellerWins=false`。

1. 袁嘉骏作为第一仲裁人，通过后端 `POST /orders/2/resolve?sellerWins=false`投票；也可用BE对应的钱包调用同样方法，二选一，只投一次。保存实际操作记录、回执和 `/orders/2/votes`。此时只有一票，订单应仍Disputed、托管代币不变。
2. 魏琪霖用确认的买家/第二仲裁钱包在Remix的增强合约上调用 `resolve(2,true)`，用于展示意见不一致。保存成功回执和投票详情；订单应仍Disputed，资金仍未结算。
3. 魏琪霖将第二票改为 `resolve(2,false)`。两票一致后订单变为Refunded，应产生 `ArbitrationVoted`、代币Transfer和 `OrderResolved`。保存买家收款和合约余额。
4. 查询 `/orders/2/events`，核对创建、付款、发货、争议、各次投票、最终裁决的顺序与交易哈希。第一次投票或意见冲突时的HTTP200只代表投票交易成功，不能写成仲裁已完成。

第2步的冲突演示是为验证“两人一致”的条件，两个参与者需知晓演示顺序；任何一票不一致都不会自动付款。每次操作后先等交易成功并核对状态。
