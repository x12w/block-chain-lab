# 成员 2：卖家发起订单 1 争议（可直接照做）

## 这一步要完成什么

买家已经创建并支付两笔订单，各 30 WQLToken，订单 0、1 目前均为 Paid。
你使用自己的卖家钱包，对**订单 1**调用一次 **dispute(1)**，让它变为 Disputed。
订单 0 保持 Paid，后面用于后端失败仲裁验证。

不需要重新部署合约、创建订单、approve 或 deposit；也不需要交出私钥。

## 一、确认钱包与网络

打开安装了 MetaMask 的浏览器，解锁你自己的卖家钱包。

- 卖家地址：`0xE0F0970f35FFE50dB6a6AD25ba775674D24682D2`。
- 网络：POTOS Testnet。
- RPC：`https://rpc-testnet.potos.hk`。
- Chain ID：`60600`。
- 货币符号：`POT`。
- 区块浏览器：`https://scan-testnet.potos.hk`。

如果网络已经配好，只需切换过去。钱包需有少量测试 POT 付 Gas；不需要买入代币，也不需要授权 WQLToken。
地址大小写可能不同，逐字忽略大小写核对即可；不能用买家或后端账户代替卖家。

## 二、打开并编译 Escrow.sol

1. 打开 https://remix.ethereum.org/ 。
2. 左侧文件栏若已有本仓库的 Escrow.sol，直接打开。
3. 如果没有，在 contracts 文件夹中新建 Escrow.sol，复制仓库该文件的**完整内容**：
   https://github.com/x12w/block-chain-lab/blob/main/src/main/resources/contracts/Escrow.sol 。
   也可以在本地仓库 git pull 后，上传 src/main/resources/contracts/Escrow.sol 到 Remix。
4. 打开左侧 Solidity Compiler，选择兼容的 0.8.x 编译器（例如 0.8.24），点击 Compile Escrow.sol，确认没有红色编译错误。

文件中同时定义 IERC20 和 Escrow 是正常的。IERC20 是 Escrow 调用代币时使用的接口；下一步选择的操作合约是 **Escrow**。

## 三、连接卖家钱包并加载本次新合约

1. 打开左侧 **Deploy & Run Transactions** 面板。
2. Environment 选择 **Injected Provider - MetaMask**（或当前界面对应的浏览器钱包连接选项）。
3. 如果 MetaMask 提示连接账户，选择你的卖家账户并连接。
4. 在 Remix 的 ACCOUNT 处核对是 `0xE0F0970f35FFE50dB6a6AD25ba775674D24682D2`，MetaMask 网络是 POTOS Testnet。
5. CONTRACT 下拉框选择 **Escrow - contracts/Escrow.sol**，不要选择 IERC20。
6. 在 **At Address** 旁边的地址框粘贴：

   `0xd7320d80b687766bA73997B97dAE61Ff1f9ed737`

7. 点击 **At Address**。下方 Deployed Contracts 会出现该地址的 ESCROW，展开它。

**这里点击的是 At Address，不是 Deploy。** 实验三的旧 Escrow 不是本次合约。
加载已有合约不需要填写 constructor 的 arbiter 参数，也不会发送部署交易。
如果显示 Remix VM，请先切换到 MetaMask 环境，否则看到的是本地模拟链。

## 四、先读取订单 1，确认没有操作错

在刚展开的 ESCROW 中找到蓝色读取函数 **getOrder**：

1. 输入 `1`，点击 getOrder（若函数收起，先展开填写 id）。
2. 展开返回结果，应看到：

| 字段 | 预期值 |
|---|---|
| buyer | 0x5a435c43Ca006bE1688d0D7B95194327528EAB26 |
| seller | 0xE0F0970f35FFE50dB6a6AD25ba775674D24682D2 |
| token | 0xB7dA837F93A5448ca0762B80862d053daf9715B3 |
| amount | 30000000000000000000（30 个） |
| status | 1，即 Paid |
| description | route A disputed order |

若已经是 **4（Disputed）**，说明争议已经发起，不要重复发送，直接查找已有交易哈希并回传。
若是其他状态，或地址/金额不符合，先把查询结果发给组长核对。

订单的 deadline 即使已经到期，也可以继续：本合约 dispute 仅要求当前状态 Paid、调用人是买卖一方，不检查 deadline。

## 五、发送唯一需要的交易：dispute(1)

1. 找到橙色写入函数 **dispute**，参数 id 填 **1**。
2. 确认 Remix 顶部 **VALUE 为 0**；此调用不附带 POT，只付 Gas。
3. 点击 dispute；MetaMask 弹窗中核对当前网络、发送账户以及交互合约为上面的新 Escrow。
4. 确认这笔测试网合约调用，等待交易完成。
5. 在 Remix 下方终端展开对应交易详情，或在 MetaMask 的活动中打开这笔交易，复制完整交易哈希。
6. 用区块浏览器打开该交易，确认 **Status 为 Success**，From 是你的卖家地址，To 是本次新 Escrow。

如果 Remix 显示 RPC 错误，**先查 MetaMask 活动/浏览器中的交易结果，并再次 getOrder(1)**，不要立即重复点。
交易已成功且状态已是 4，就无需重发。

## 六、确认结果并截图

再次调用 **getOrder(1)**，应看到 **status = 4（Disputed）**。
再调用 **getOrder(0)**，应仍是 **status = 1（Paid）**。这两个查询不会消耗 Gas。

至少保存这三张图，文字要清晰：

1. **卖家发起争议成功**：Remix 当前卖家 ACCOUNT、新 Escrow 地址及 dispute(1) 成功交易详情；保存完整哈希。
2. **订单 1 争议状态**：getOrder(1) 展开的 buyer、seller、amount、status=4、description，连同合约地址。
3. **区块浏览器成功回执**：争议交易的完整哈希、Success、From=卖家、To=新 Escrow、区块号。

可再补一张 getOrder(0) 仍为 Paid 的图；如果浏览器显示解码日志，也保存 OrderDisputed(id=1, by=卖家)。
截图不要包含私钥、助记词、钱包导出页面。只截签名前确认窗口不够，还需要成功后的回执和状态。
建议文件名：member2-dispute-success.png、member2-order1-disputed.png、member2-dispute-explorer.png。
